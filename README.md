# Cost Allocation Reconciliation (Streamlit)

Guided app around the `references/transform_table4.py` workflow. It splits multi-invoice cells in the
bag table (TABLE 4), recalculates each bag's charge per invoice from the invoice table (TABLE 1), and
reconciles bag-allocated totals against invoice totals. The calculation logic lives in `core/` (no UI
code) and is regression-tested against the original script.

## Run it (Windows PowerShell)

```powershell
.\run.ps1          # first run creates .venv and installs requirements, then starts the app
# or: run.bat
# or manually:
py -3.12 -m pip install -r requirements.txt
py -3.12 -m streamlit run app.py
```

Put the two CSV exports in `inputs/` (or any folder you type into the Upload page; the page falls back
to `references/` if `inputs/` is empty). Browser upload also works (limit 1 GB, set in
`.streamlit/config.toml`), but picking from a folder is much faster for the 250 MB bag file.

Pages: **1. Upload & check** -> **2. Run** -> **3. Results** -> **4. Export**, plus **5. Run history**
(open a past run, compare two runs).

Every run writes a timestamped folder `runs/YYYYMMDD_HHMMSS/` with the transformed TABLE 4 (CSV, optional
Parquet), `reconciliation.csv`, `reconciliation.xlsx` (with issue sheets), `transform.log`,
`transform_warnings.csv` and `run_metadata.json` (input names, sizes, SHA-256, row counts, mode,
tolerances, summary counts).

## Performance and memory (full files, 584,751 bags)

About 3 minutes end to end on this machine (original script: about 4m46s). Roughly 70 s is read +
transform, about 60 s is writing the 280 MB CSV and about 30 s is the reconciliation. Peak memory was about
2.5 GB; allow 4-6 GB free to be safe. The loaded files are cached, so re-running with other settings does
not re-read the CSV.

## Tests

```powershell
py -3.12 -m pytest                 # unit tests + regression on a 2,033-row slice (~10 s)
py -3.12 -m pytest -m full         # regression on the FULL files vs golden/full (~3 min, needs references/ + golden/)
```

* `tests/test_regression.py` runs the new core and compares the transformed TABLE 4 and the reconciliation
  with the **original script's output** on the same input (default and full-recalc modes), within 1e-6.
  Golden files were generated by `tests/make_samples.py` (it runs the original script).
* `tests/test_transform.py` covers single / many / duplicate IDs, trailing semicolons, whitespace and case,
  invoice missing from TABLE 1, zero tonnage, per-bag demurrage, invoices with no bags, the match boundary,
  credit notes and input immutability.

## What changed versus the original script (please review)

1. **Match / Mismatch rule (your request).** The original used `|diff| < $0.01`. The app uses
   `|diff| <= $1.00` (Mismatch only when the difference is below -$1.00 or above +$1.00). On the full data:
   2,760 / 204 became **2,864 Match / 100 Mismatch**. The Difference column and all bag charges are
   unchanged. The regression test checks Match? against the golden Difference with the new rule.
2. Dead code removed: the `skip_recalc` and `t1_charge is None` branches.
3. Tolerances are named constants in `core/config.py` (bag check $0.10, invoice warning $1.00, match
   $1.00) and can be changed on the Run page (Advanced).
4. The CSV reader accepts a UTF-8 BOM (and falls back to Windows-1252); the original would have put the BOM
   into the first column name. Wrong delimiter, empty files and header-only files stop with a clear message.
5. The per-row `iterrows` loops are replaced by vectorised grouping. Rounding uses numpy's `round(.., 6)`
   instead of Python's, which can differ in the 16th digit and is far inside the 1e-6 test tolerance.
6. Log wording is unchanged; warnings are also kept as structured rows (type, category, invoice, bag,
   amount) for the filterable Warnings tab and `transform_warnings.csv`.

## Behaviours inherited from the original on purpose

* If the **first** invoice ID in a multi-invoice cell is not in TABLE 1, the primary cell keeps its raw text
  (semicolons included); the "semicolons after" KPI then shows a non-zero value and a warning.
* Overflow columns are numbered by position, so a skipped unknown ID leaves an empty slot.
* Duplicate IDs in one cell are each processed and each counts towards the invoice's tonnage / bag count.
* Invoices with a zero amount and no bags are not listed in the reconciliation.
* `BASE FREIGHT CHARGE ($)` and `FUEL SURCHARGE ($)` are passed through and not reconciled.

## Findings from the data (full files)

* Reference numbers reproduced exactly: 584,751 bags, 157,274 multi-invoice cells before / 0 after,
  2,964 reconciliation rows, 5,447 bag-level and 100 invoice-level warnings, Performance Bonus 11 invoices
  / $560,514.66 all matching.
* **Sub-invoice IDs (`805971/2`) are not an ID-format mismatch.** TABLE 4 does use the `/n` format (278
  distinct IDs). The 15 zero-bag sub-invoices, and the other 70 zero-bag IDs, appear nowhere in TABLE 4 in
  any category - nothing references them. The Issues tab includes a diagnostic table for this.
* 4 of the 85 "no bags" invoices are credit notes (negative amounts): the group is $5.42M gross but
  $4.98M net. The Issues tab flags them and can filter them in or out.

## Open points / not verified

* Not tested on pandas 3.x (this environment has pandas 2.3.1); the code avoids version-specific string
  behaviour but it has not been run there.
* The app has been exercised with Streamlit's headless test runner and a full-file end-to-end run, not by
  clicking through a browser, so check layout and wording on screen.
* The download buttons for the large transformed TABLE 4 are hidden behind a checkbox because Streamlit loads
  the whole file into memory; use the run folder instead.
